# ADR-004：正式实现前先做 12 候选 UI 预览并由用户选型

- 状态：已接受（阶段 0.5 硬门控，已执行完毕）
- 日期：2026-09-28（选型）/ 2026-09-30（v1.1 增补）
- 关联：[ui-selection.md](../ui-selection.md) · [design/ui-preview/index.html](../../design/ui-preview/index.html)

## 背景

UI 是本项目的核心交付面（320×230 弹出面板），但"好看/顺眼"无法用验收标准客观定义——风格分歧若发生在代码完成后，返工成本最高。需要在写第一行正式 UI 代码之前消除风格不确定性。

## 决策

**流程硬门控：正式实现前，先产出静态 HTML 预览页——4 种风格 × 各 3 候选 = 12 个候选项，每候选渲染 4 种状态组合（高峰/空闲 × 浅色/深色）共 48 个面板；经两轮验收修正渲染缺陷后提交用户选定；选定结果（A1）连同精确设计参数固化为绑定规范**（[ui-selection.md](../ui-selection.md)），对后续所有 UI 实现有约束力。

## 理由

1. **把"审美决策"前置到成本最低的环节**：改 HTML 参数以分钟计，改 WPF + 重新发布以小时计。
2. **预览即规范**：候选页中的 CSS 参数（320×230 布局、14px 圆角、完整四态色板、字号/字重/间距）被逐值提取为 A1 规范，实现与验收都有客观对照（阶段 5 测试按规范值逐像素取证）。
3. **两轮验收拦截了会误导选型的缺陷**：首轮发现 B/C 两组 6 候选的 idle 组合缺失材质变量——12 个空闲面板背景透明失效、6 个"空闲·深色"面板浅底白字不可读；修复（材质变量提升到主题层）后才提交用户，保证用户看到的是真实效果。
4. **用户参与感与责任边界**：12 候选 → 用户选定 A1（无融合项）→ 记录在案；后续 v1.1 需求变更（右缘停靠/拖动/钉住）也走"§7 行为增补"修订规范而不是口头约定。

## 后果

- 正面：A1 参数成为阶段 4 全部 UI 的验收基线，测试报告能逐值核对（面板尺寸/圆角/15 项色板/字号全部命中）；风格返工为零。
- 负面：多花了一个阶段的流程时间；HTML 预览与 WPF 渲染存在固有差异（如 WPF 无 CSS `letter-spacing`，"总余额" 3px 字距以空格近似），需登记口径。
- 中性：落选的 11 个候选保留在预览页中，未来迭代可回溯参考。

## 替代方案

| 方案 | 结论 |
| --- | --- |
| 直接按开发者审美实现 | 否决（风格分歧后置 = 最大返工风险） |
| 只做 1 个候选确认 | 否决（无可对比性，用户决策依据不足） |
| 用 XAML 原型做预览 | 否决（迭代慢、且"预览即规范"的参数提取不如 HTML/CSS 精确直白） |
