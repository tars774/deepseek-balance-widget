# ADR-003：心跳 = UI 线程 DispatcherTimer + 伺服式绝对对齐

- 状态：已接受（探针 E 实测定夺）
- 日期：2026-09-29（探针 E 实测修订）
- 关联：[scheduler-design.md §2](../scheduler-design.md) · [probe-results.md](../probe-results.md)

## 背景

定时巡查机制是全应用的时间基准与状态驱动源（1 秒心跳驱动倒计时/进度/翻转沿/跨天/余额调度）。候选方案：

1. UI 线程 `DispatcherTimer(1s)`；
2. 专用心跳线程（可更高精度）；
3. `DispatcherTimer` + `timeBeginPeriod`（提升系统计时器分辨率）。

约束：秒级 UI 精度即可（显示粒度本身 1s）；UI 更新必须在 UI 线程；睡眠唤醒后要能自动补判；系统计时器量化 ~15.6ms。

## 决策

**采用 UI 线程 `DispatcherTimer(1s)`，并叠加"伺服式绝对对齐"**：每 tick 用单调时钟（Stopwatch）测量实际触发时刻与目标槽位的带符号误差 `e`，按下式重排：

```text
Interval = clamp(Heartbeat − e, 250ms, 2000ms)     # 伺服式重排
若 |e| ≥ 1s（长停顿）：跳过被吃掉的槽位，补一次而非爆发多次
```

**否决专用心跳线程与 timeBeginPeriod。**

## 理由

1. **零封送成本**：心跳天然在 UI 线程，4 类事件零封送直接更新 WPF；专用线程每次更新都要 `Dispatcher.Invoke/BeginInvoke`，多一道竞态面（探针 E 对 4 类事件逐一断言 UI 线程触发全过）。
2. **失败模式友好**：tick 异常进入与 UI 相同的全局异常兜底链；专用线程异常若未捕获即静默死亡（心跳停摆无感知）。
3. **量化漂移可被伺服对齐消除**：系统计时器量化（~15.6ms）本身不可避免，但**累积漂移**可以。探针 E 三模式对照实验（各 90–330 tick 真实时钟浸泡）：

   | 模式 | 5 分钟级累计漂移 |
   | --- | --- |
   | 朴素 `Interval=1s` | +44.1ms@90tick（0.03–0.85 s/分钟，逐轮累积） |
   | 直觉补偿公式 | **−2978.6ms**（把迟到做了二次补偿，每 3–8 tick 多打 1 拍） |
   | **伺服式（采用）** | **+2.5ms**（验收方独立复测 +7.2ms；要求 <1s） |

4. **平台语义的实测修正**：探针发现 WPF 在 Tick 处理器内修改 `Interval` 时按**旧到期点**重排（仅 Interval 恒定时才按触发时刻重排）——伺服式公式在两种平台语义下均收敛，因此对语义不确定性鲁棒。
5. **精度需求封顶**：倒计时按"下一切换点 − 当前时刻"的**绝对差值**每 tick 重算（永不累加），单 tick 晚到甚至跳拍，下一 tick 显示值立即回正——亚秒精度（专用线程/timeBeginPeriod 的唯一优势）对秒级 UI 无意义，而其功耗、封送、异常处理代价都是真实的。

## 后果

- 正面：实测 mean 1000.0ms、漂移 ±ms 级、单 tick 处理 0.09ms、稳态 CPU 1–2%·核、零未处理异常；睡眠唤醒后首个 tick 基于 `ITimeProvider` 绝对时间自动补判（无需额外代码路径）。
- 负面：对齐逻辑本身有认知成本（已被 [scheduler-design.md §2.3](../scheduler-design.md) 完整文档化 + 集成测试覆盖）；clamp 下界 250ms 防忙转是必须遵守的实现约束。
- 中性：高负载下 tick 可能迟到（观察项），跳槽位路径保证"补一次不爆发"。

## 替代方案

| 方案 | 结论 |
| --- | --- |
| 专用心跳线程 | 否决（封送/异常/睡眠三重代价，亚秒精度无用武之地） |
| DispatcherTimer + timeBeginPeriod | 否决（提升全局计时器分辨率影响整机功耗，换不来秒级 UI 可感知收益） |
| 朴素 `Interval=1s` | 否决（漂移逐轮累积，实测不可接受） |
